Get started

Future releases will be available only through this website. No approved download is available yet. npm and crates.io distribution is retired; historical releases retain their original license terms.

Already have Kineti 0.6.1? The commands below describe that historical native gate for macOS and Linux on x64 and arm64. Its installed native executable does not require Node.js or Bun. Check your version before following these instructions:

kineti --version

From your project directory, preview initialization with your own project goal:

kineti init --goal "Your project goal"

Review the proposed changes and backups. To apply the setup, run:

kineti init --goal "Your project goal" --apply

A new project requires an explicit goal. Kineti preserves an existing locked goal. If Codex is detected, setup can propose MCP registration; restart Codex after applying changes. Use kineti status to inspect state and spending; unresolved accounting or damaged records can block it.

Record and check a test

Run a supported test command through Kineti. The example below assumes a Rust project with a tests directory and Cargo installed. Replace the command and required path with those for your project.

kineti test run --label tests --required-test tests -- cargo test
kineti test check --label tests --expect-argv '["cargo","test"]'

The first command runs the test and records evidence. The second checks that evidence, including the expected command and whether recorded inputs are still current. Kineti requires a supported test summary and an existing required test path; a successful process exit alone is not enough.

When inputs change or evidence is stale, run the tests again and check the new evidence. A signature confirms record integrity, not that a test command reported honestly.

Check a participating CI workflow

Run the gate before the release command in the workflow you choose:

kineti ci --require-evidence tests

CI checks the required evidence, project gates and reported spending policy. It can block the commands that explicitly use it; it does not automatically intercept other commands. Configure required labels in .kineti/gate.json or supply them explicitly.

Kineti can expose tools through MCP. The 0.6.1 integration was tested on macOS arm64 with Codex 0.163.0-alpha.11.2 and 0.164.0, without a model turn. Other Codex versions, Cursor and Antigravity are unverified.

Reported spending

The example below records a reported amount. Use it only if the stage, token counts and amount match your actual records; replace the example values before running it. Then check the configured limits:

kineti spend log --stage build --model reported --tokens-in 0 --tokens-out 0 --usd 0.25
kineti spend check

Amounts are reported by the operator; Kineti does not verify provider bills. Unknown costs, unresolved reservations or damaged accounting can stop the check. Do not replace an unknown amount with zero. kineti spend recover previews recovery; applying a recovery requires an exact reviewed proposal and supporting evidence.

Register an undo action

Register the exact command needed to reverse a change before making it. For example, only if generated-file is a disposable file you intend to create:

kineti undo push --label cleanup -- rm generated-file
kineti undo rollback
kineti undo rollback --yes

The first rollback command previews; the second applies. Undo runs registered actions newest first. If completion is uncertain after interruption, inspect and resolve that state before replaying.

What Kineti can and cannot establish

  • Records can detect changed inputs and support checks in participating workflows.
  • Signed records do not prove that tests were honest; a command can fabricate output.
  • Reported costs are not provider bills, and a confirmation flag does not prove a person acted.
  • Kineti does not provide automatic interception, protected writes, or atomic permission for later writes.
